## What the new protection means in plain language

Each enrolled device has its own private keys generated by Apple's Secure
Enclave. 2ndPass asks the Enclave to use those keys; it does not receive their
plaintext private values. An account groups a person's approved devices and
their role. Signing into the same Apple Account is not itself device approval.

Every password has a separate random encryption key. The vault stores a small
encrypted copy of that key for each approved device and any configured hardware
recovery device. Reading the catalog opens its key only. Reading one password opens
that password's key; it does not unlock a vault-wide key that can decrypt every
password. The new engine retains no symmetric keys between calls.

The unwrapped password key and password **do** enter application memory. AES,
HPKE's derived state, Swift/Foundation data, and plaintext are not promised to
remain inside the Enclave. 2ndPass and commands receiving a password can read it.
Owned temporary buffers are wiped where practical; framework copies and strings
cannot be comprehensively erased. Authorized malicious code can ask the hardware
to perform permitted operations and copy their results.

Removing a device or member creates fresh keys and ciphertext for every current
secret, and future revisions omit removed recipients. This cannot erase old
copies of passwords, ciphertext, or keys. Offline devices cannot learn about a
removal until they reconnect. Recovery is hardware-only, as explicitly selected by the user. Keep a separate
recovery device and an encrypted backup with an independently recorded checkpoint.
No v6 software recovery private key is generated, stored, imported, or exported.
If every authorized and recovery device is lost, the vault cannot be recovered,
even with the encrypted backup and restored Apple Account access. The initial
experimental portable recovery provider was removed after this decision.

## Reproduction

From the repository root:

```sh
swift test --disable-automatic-resolution --filter MopVaultNextTests
swift build --target MopVaultNextCheck --disable-automatic-resolution
swiftc -module-cache-path /tmp/2ndpass-next-module-cache \
  prototypes/vault-next/enclave.swift -o /tmp/2ndpass-enclave-probe
/tmp/2ndpass-enclave-probe
/tmp/2ndpass-enclave-probe --deny
/tmp/2ndpass-enclave-probe --preauthorize
swiftc -parse-as-library -module-cache-path /tmp/2ndpass-next-module-cache \
  prototypes/vault-next/cloud.swift -o /tmp/2ndpass-cloud-probe
```

The default standalone Enclave probe tests hardware crypto without user-presence
ACLs; `--deny` and `--preauthorize` test the intended ACL policy. Production
`EnclaveDevice` always creates `.privateKeyUsage` + `.userPresence` keys.

For Keychain/CloudKit checks, provision and sign a disposable app-like bundle
containing the appropriate executable, matching profile and narrow access group.
Use Development entitlements explicitly. The temporary executable must not
replace or launch the installed 2ndPass GUI. Run it from a user login context.

`MopVaultNextCheck engine` exercises the new implementation with disposable keys.
`keychain-create SCOPE MEMBER_UUID` requires a scope of `mop-v6-probe-UUID`;
`keychain-open SCOPE MEMBER_UUID EXPECTED_FINGERPRINT` reopens exactly that item.
These commands never delete an identity. Authentication is required.

`cloud-engine` runs the actual v6 transport/engine/journal against a freshly
generated Development-only `mop-v6-probe-UUID` zone. It retains the exact encrypted root
locally before initialization and prints the zone and local directory. It never
opens an existing vault, creates a share, or deletes data. Hardware keys for this
disposable engine check are ephemeral; its test password is a fixed public value.

The cloud prototype takes `CONTAINER` followed by:

- `inspect`: lists only probe zones.
- `create`: creates a fresh `2ndpass-next-probe-UUID` zone and a `MopNextProbe` record
  with a disposable marker. This schema is Development-only probe data.
- `race private|shared OWNER ZONE`: two competing conditional saves.
- `barrier private|shared OWNER ZONE`: same-value CAS plus rejection of an old-version save.
- `prepare ZONE`: creates/updates a nonpublic share; no additional participant.
- `share-info ZONE`: reads owner/current-participant aliases and permission state.
- `share ZONE PARTICIPANT_RECORD_ID`: explicitly adds the intended test account;
  prints a URL for manual delivery. Do not run this for an unconfirmed recipient.
- `accept URL`: validates the container and probe-zone prefix, accepts, and fetches
  through the shared database using the actual owner name from metadata.

Commands refuse ordinary 2ndPass zone names and provide no delete command. Bound
manual executions to 120 seconds; an interrupted cloud call may still complete.
Keep the printed probe locator and inspect it before repeating a mutation.

`service-engine` additionally exercises the public application service, using a
fresh local registry and separate recovery request. It requires interactive
hardware authentication; the attempted run did not complete authentication.
The v6 CLI hardware smoke script supports creation without recovery or an optional
independently verified recovery request, and checks the executable version before
creating a test vault.
Its updated live workflow has not been run.
