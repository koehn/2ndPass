# System assessment — September 24, 2026

Scope: the current working tree, including uncommitted v5 account identities,
mobile support, shared UI, and OTP changes. This is a source review and local
test assessment, not a certification or a live-cloud penetration test. Existing
user changes were preserved. No production vaults, Keychain identities, account
settings, or recovery credentials were accessed or modified.

## Assessment

Mop has a sound modular foundation and unusually substantial failure-path testing
for its size. Its cryptographic storage, conditional cloud publication, and local
file handling show deliberate security engineering. However, the v4-to-v5
transition is incomplete across CLI behavior, historical recovery, and operational
documentation. I would not release this snapshot as a finished password manager
before correcting the findings below and recording signed physical-device
acceptance for the new identity model.

## Findings

### P1 — CLI strict-biometric policy is not persisted or consistently honored

`Sources/MopCLI/VaultCommands.swift:96` authenticates initialization using the
flag for that invocation, but initialization never writes
`account-authentication.json`. Import and recovery repeat that pattern at lines
216 and 286. Subsequent reads use `CommandVaultAuthorization.swift:57–60`, which
defaults to non-strict authentication when this file is absent. The CLI v4
conversion at lines 54–68 also fails to preserve the legacy device's strict
setting. The native service does explicitly persist policy during setup/conversion.

Thus, in a fresh CLI state directory, `vault init --strict-biometrics` is followed
by reads that allow ordinary owner authentication, including password fallback.
Likewise, a legacy strict device converted through the CLI loses that restriction
on later v5 access. Initialization/import/recovery also consult their flags rather
than an existing saved strict policy.

This is confirmed by source control flow, not a live biometric experiment.
Centralize account-authentication policy for both interfaces, persist it before
publishing creation/conversion, honor existing stricter policy, and add tests
covering subsequent commands. Do not describe v5 strict mode as OS-enforced
`biometryCurrentSet` protection: the synchronized identity item has no such ACL.

### P2 — Conversion leaves pre-v5 history inaccessible to normal restoration

`Sources/MopVault/VaultSession.swift:413–417` requires the same opener to be a
recipient of the historical revision and a device/member of the current one.
Conversion removes the legacy device slots and switches to the new account
opener. That opener was never a recipient of the v4 history. A recovery-key
session is rejected by the current device/member check as well.

A temporary fixture-only regression probe reproduced this: create a v4 secret,
retain a revision, update it, convert to v5, and call `restore` on the retained
revision. Both the account session and a recovery session return
`deviceNotEnrolled`; the current value remains readable. The probe was removed
after execution. Historical ciphertext is retained, not destroyed, but the normal
`vault resolve` route cannot restore it.

Provide an explicit restoration operation with separate current authorization and
historical decryption credentials, resealing under current membership. Until then,
document this limitation prominently instead of merely saying conversion preserves
history. Never reinstate historical recipients when restoring contents.

### P2 — The retained trust command uses only the obsolete device credential

`Sources/MopCLI/VaultCommands.swift:251–264` exposes `vault trust` but opens
`LocalDevice` unconditionally. A fresh v5 installation has no legacy device
credential; a converted vault has no slot for it. Consequently the advertised
command cannot establish trust on a v5 vault, even with correct independent
fingerprint evidence. This is a source-confirmed incompatibility, not a bypass:
normal account-owned access establishes its own trust through the authenticated
account identity.

Either make this command explicitly v4-only with accurate help, or route v5
evidence verification through account authorization. Test both formats.

### P2 — Operational documentation mixes incompatible security models

`docs/ACCOUNT-IDENTITY.md` accurately describes much of v5, and the banner in
`docs/SECURITY.md` labels its older material historical. Nevertheless, the main
security guide still intertwines current file/cloud requirements with lengthy
device-enrollment and hardware-ACL instructions. Readers cannot reliably use it
as an operational runbook.

Concrete contradictions include:

- `docs/VALIDATION.md:5–6` says there is no migration and software keys occur only
  in tests, whereas v5 intentionally uses synchronized software keys.
- `docs/man/mop.1:94–125` describes v4 exports and removed device request,
  enrollment, and revocation commands.
- `README.md:142` still tells new Macs to enroll.
- Mobile/manual acceptance lists continue to emphasize device enrollment and
  revocation, while v5 deliberately has no independent per-device revocation.

Rewrite the active runbooks around v5; move v4 instructions into a clearly
separate migration reference. Keep historical validation results explicitly dated
and separate from current release gates. The September 23 audit does not establish
the safety of the subsequently introduced account-identity design.

## Security design

Positive controls include per-record AES-GCM keys, HPKE context binding, signed v5
membership and revisions, account-scoped trust/cache state, verified versus merely
downloaded snapshots, rollback watermarks, conditional head updates, uncertain
commit journals, bounded persistent snapshots, atomic private outputs, and
explicit subprocess execution without implicit shell fallback. Tests exercise
tampering, conflicts, interrupted writes, account changes, lock races, and delayed
Keychain delivery. Dependency versions/revisions and CI checkout actions are pinned.

The major architectural tradeoff is intentional: one exportable account identity
now opens all owned vaults on synchronized devices. LocalAuthentication gates the
application's retrieval path; it is no longer an ACL on each use of a
non-exportable enclave private key. `SynchronizedIdentityStore.swift` stores the
64-byte private material with `kSecAttrAccessibleWhenUnlocked` and synchronization.
Apple documents that accessibility as available while unlocked, and that
synchronizable items cannot use `ThisDeviceOnly` accessibility classes:
[accessibility](https://developer.apple.com/documentation/security/ksecattraccessiblewhenunlocked),
[synchronization constraints](https://developer.apple.com/documentation/security/ksecattraccessible).

This supports simpler onboarding, but compromise of the account identity has an
account-wide scope, and Mop has no implemented account-key rotation or independent
device-revocation protocol. Treat compromise recovery and ownership transition as
explicit product limitations. A removed device's historical data cannot be erased
cryptographically after it has obtained keys/plaintext. Fresh-device rollback
detection is also limited by the absence of previously observed local state.

No new cloud-to-plaintext bypass was demonstrated by this review. That statement
does not establish the absence of vulnerabilities. Private-key memory handling,
Apple enforcement, and real server behavior need deeper validation than fixture
tests can provide.

## Maintainability and system design

The package boundaries between Core, Vault, Keychain/Auth, CloudKit, AppSupport,
and UI are useful. Native clients share crypto/storage logic, and dependency
injection makes failure cases testable without real secrets.

The main maintainability risk is orchestration duplication. CLI setup/import/
recovery and native service setup implement related authentication decisions
separately; the strict-policy defect is a concrete consequence. Move policy and
account lifecycle into a shared service while preserving separate CLI/UI lifetimes.

`AppModel.swift` is about 937 lines and `VaultService.swift` about 852, combining
session control, CRUD, recovery, synchronization, and legacy pairing. Pairing
protocol/coordinator code and the old subprocess client remain compiled despite
their removal from the normal app flow. Isolate necessary migration support and
remove unused operational paths after checking compatibility requirements.

Scalability is bounded but not cheap: snapshots are capped at 16 MiB, mutations
serialize/authenticate the record table, and history traversal can reconstruct
many full revisions sequentially. Benchmark representative vault sizes and long
histories before promising large-vault performance. Cloud history and abandoned
uploads still lack automatic pruning.

Compiler-cache and pseudo-terminal restrictions initially blocked two checks;
reruns with the required local permissions passed. Those environment failures
were not classified as product defects.

This review did not rerun mobile simulator/device builds, verify a newly packaged
release, perform a full dependency-advisory or historical-secret scan, or exercise
live CloudKit and iCloud Keychain. The existing docs themselves record outstanding
signed-device and Production acceptance. Required release evidence includes real
Mac/iPhone/iPad identity delivery, matching access groups, strict/default policies,
conversion and backup recovery, account changes, offline/reconnection behavior,
lost responses, and distribution-signed Production smoke tests.

Recommended order: fix authentication policy; repair or explicitly constrain
history/trust behavior; consolidate v5 documentation; complete physical acceptance;
then simplify legacy orchestration and measure scale.
