## Scope and method

Reviewed all production Swift sources, the package manifest and dependency lock, shell/Python packaging and release tooling, the Homebrew formula/workflow, relevant tests, and security/operational documentation. Traced these boundaries:

- User authorization → Keychain access group → Secure Enclave key operation.
- Untrusted CloudKit records → structural validation → local trust pin → authenticated index/record decryption.
- Revision publication → conditional head save → local journal and rollback watermark → offline snapshot.
- Plaintext → CLI output/child environment/files → GUI memory and clipboard.
- Source/dependency inputs → signed bundle → installation and shell resources.

Used source review, the full test suite, unsigned CLI smoke tests, synthetic adversarial probes, signature verification, and a pattern scan of working sources and 139 historical Git blobs. Checked the dependency's public security advisories. This was not a formal cryptographic proof, exhaustive fuzzing campaign, or audit of Apple framework internals, GitHub account settings, or the live CloudKit schema/permissions.

Severity reflects prerequisites and actual impact. The attacker model includes hostile cloud responses without decryption keys, unintended plaintext retention, and observation of an inactive app. Same-user arbitrary code execution, a compromised OS, deliberately malicious authorized child processes, and possession of the recovery private key remain outside the application's stated protection boundary.

## Findings

### MOP-01 — Medium: clipboard protections do not cover all secret-copy paths

**Locations:** `Sources/MopApp/AppModel.swift:129–142`; `Sources/MopApp/ContentView.swift:147–148`; clipboard cleanup at `Sources/MopApp/AppModel.swift:63–67`.

The explicit Copy value action writes a plain string to `NSPasteboard.general` with `clearContents()` and `setString()`. It does not request `.currentHostOnly`. With Universal Clipboard enabled, a secret is eligible to leave the Mac for another device on the Apple Account, independently of that device's enrollment in the Mop vault. Apple documents `.currentHostOnly` as restricting pasteboard contents to the current device. [Apple API reference](https://developer.apple.com/documentation/appkit/nspasteboard/contentsoptions/currenthostonly?changes=_8_5).

There is also an unmanaged copy path: the revealed plaintext `Text` has `.textSelection(.enabled)`. Copying that selection uses the native text-copy behavior, bypassing the code that records `clipboardChange` and starts the 30-second clipboard task. Revealing starts only the conceal task. Consequently, a user can reveal a value, copy the selected text, then lock the app or wait 30 seconds; Mop has no recorded pasteboard change count for that copy to clear. The plaintext display disappears while the clipboard entry remains. This differs from the documented clipboard expiration behavior.

**Impact and prerequisites:** user-initiated copying can retain or synchronize plaintext beyond the intended lifetime/device. This does not bypass authentication or make arbitrary local clipboard readers unable to see deliberately copied secrets. Clipboard history tools are already a documented limitation; the missing device restriction and unmanaged copy path are additional controllable exposures.

**Evidence:** confirmed source paths and the platform API contract. A live clipboard or cross-device transfer was not exercised, to avoid replacing the user's clipboard. The native selection sequence should be checked with a synthetic value in GUI acceptance testing.

**Fix:** centralize secret clipboard writes; use `prepareForNewContents(with: [.currentHostOnly])`; retain the existing change-count ownership check and expiration. Disable native selection on revealed values, or route its Copy action through the same helper. Consider a confidential-content marker for cooperative clipboard managers, without treating it as enforcement. Test explicit copy, selected-text copy, timeout, lock, sleep, and preserving another application's newer clipboard content.

### MOP-02 — Medium: an operation in flight bypasses automatic locking on app deactivation

**Locations:** `Sources/MopApp/MopApplication.swift:11–15`; `Sources/MopApp/AppModel.swift:105–114`.

The inactive-app handler calls `conceal()` but skips `lock()` whenever `model.busy` is true. That exception handles authentication dialogs, but it also applies when the user switches applications during a network operation. It does not invalidate the generation token. `unlock()` subsequently accepts its result based only on that token and publishes reference names with `authenticated = true`; it never checks whether Mop is active. No completion handler performs the deferred lock.

**Reproduction:** start an index refresh with a delayed fake CLI; run the exact deactivation-handler logic while `busy == true`; allow the command to finish. The included model probe confirms that the index remains populated and authenticated. An already visible index similarly remains present when the app deactivates during another operation that does not clear it.

**Impact and prerequisites:** an inactive window can display sensitive namespace/item/field names after authentication, contrary to the documented switching-apps lock behavior. This is a metadata disclosure, not a bypass of fresh authentication for secret values; `read(copy:)` does check `NSApplication.shared.isActive` before revealing/copying its result.

**Evidence:** `2026-09-23-gui-probe.swift` passed with:

```text
CONFIRMED: inactive-handler path permits delayed unlock to publish the private index.
```

The probe exercises the production model with a synthetic subprocess and models the exact inactive-handler branch. It does not mount a native window or simulate a real Touch ID dialog.

**Fix:** track scene activation independently of command execution. Hide the index immediately on deactivation and prevent completions from restoring visible state while inactive; perform a deferred lock when a command completes in the background. Preserve the documented behavior that an already submitted mutation may finish, and test authentication-dialog focus transitions separately from switching to another app.

### MOP-03 — Medium: rejected cloud records accumulate permanently in the local cache

**Locations:** `Sources/MopCloudKit/CloudVault.swift:46–63`; `Sources/MopCloudKit/CloudCache.swift:48–59`.

`revision()` writes a downloaded blob into the persistent cache immediately after comparing its SHA-256 with the manifest-supplied hash. The same untrusted service supplies both values. The write occurs before checking the aggregate size, decoding the record, reconstructing the revision, or verifying its expected digest. Invalid blobs remain after the command fails. `putBlob()` has no total storage budget or eviction policy.

**Reproduction:** a fake transport serves a structurally plausible manifest containing the hash of a 64 KiB non-JSON payload. `vault.sync()` rejects the record, but its `.blob` file survives. Repeating with three distinct payloads leaves three files totaling 196,608 bytes. No device opener or authentication is involved.

**Impact and prerequisites:** an attacker able to alter cloud records/responses can grow local disk usage across failed syncs or ordinary online commands, without learning any encryption key or passing vault authentication. A response is size-bounded, but retained storage across attempts is not. Exhaustion requires repeated downloads and sufficient volume; no disk-exhaustion stress test was performed. This extends service-level denial of service into persistent local disk consumption. It does not promote invalid data to the verified offline snapshot.

**Evidence:** `2026-09-23-cloud-probe.swift` produced:

```text
CONFIRMED: three rejected syncs retained 3 malformed blobs, 196608 bytes, without authentication.
```

**Fix:** stage downloads in a bounded temporary area; reject malformed/oversized records before persistent writes; discard new staged blobs on reconstruction/digest failure. Enforce an overall cache budget and eviction policy even for structurally valid unverified revisions. Preserve data needed by the verified offline snapshot and pending commits. A content hash alone must not authorize unlimited retention.

|---|---|
| Authentication and key access | Fresh `LAContext`, zero biometric reuse setting, invalidation on close/failure, explicit user-presence/current-biometry ACLs, device-only nonsynchronizing Keychain storage, and an actual unwrap proof on device open. Hardware enforcement still needs live acceptance. |

| Encryption and integrity | Independent AES-256-GCM record keys, CryptoKit HPKE wraps with vault/role/purpose binding, authenticated record-table digest, canonical index checks, size limits, and recipient validation. No homemade cipher construction was found. |
| Trust and rollback | Independent key/identity pins reject public-key substitution; CloudKit watermarks reject lower-generation and same-generation alternative snapshots. Missing trust is not automatically bootstrapped from successful decryption. Freshness remains limited by what a device has already observed. |
| Revocation and history | Removal rotates index and record keys. Restoration requires current authorization and re-encrypts selected contents for current recipients. Historical ciphertext remains decryptable to its original recipients by design. |
| Cloud writes and offline access | Conditional head updates, writer leases, uncertain-commit journals, account-scoped caches/defaults, explicit offline reads, no queued offline mutation, and separation of downloaded versus authenticated snapshots are covered by fixture tests. Real server concurrency is not established by those tests. |
| Files | Atomic output with exclusive creation, symlink/type checks, private permissions, inherited ACL removal, and protected-state path checks. A candidate case-alias bypass was tested and rejected because Foundation resolved the path to its actual case; it is not a finding. |
| CLI/processes | No implicit shell execution; reference inputs are validated; errors avoid arbitrary secret-bearing text; batch references resolve before output/launch; contexts close before children start. Exact-byte masking and chunk boundaries have regression coverage. Masking remains an output aid, not containment. |
| GUI subprocesses | Uses the bundled CLI path, arguments as an array, stdin for values, concurrent stdout/stderr draining, fixed failure messages, and generation checks for explicit lock. No secret logging or persistent UI preference storage was found. |

## Reproducing the targeted probes

The cloud probe compiles against the debug objects produced by the current Xcode-backed SwiftPM build. From the repository root, after `swift test`:

```sh
swiftc -parse-as-library -I .build/out/Products/Debug \
  docs/security-audit/2026-09-23-cloud-probe.swift \
  .build/out/Products/Debug/MopCore.o \
  .build/out/Products/Debug/MopAuth.o \
  .build/out/Products/Debug/MopKeychain.o \
  .build/out/Products/Debug/MopVault.o \
  .build/out/Products/Debug/MopCloudKit.o \
  -o /private/tmp/mop-cloud-audit-probe
/private/tmp/mop-cloud-audit-probe
```

Other SwiftPM build backends may place the module/object files elsewhere. The GUI probe is a Swift Testing source: place a temporary copy of `2026-09-23-gui-probe.swift` in `Tests/MopAppTests/`, run `swift test --filter SecurityAuditTests`, then remove only that temporary copy. Both probes now assert the corrected behavior; the evidence above records their original pre-fix results.
